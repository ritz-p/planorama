# Resource support matrix

Generated from provider implementation sources and runtime classification, visibility,
placement, scope and service-classification functions. Do not edit this file; run
`sh scripts/update-resource-support.sh` in the development container.

The AWS managed baseline covers all 1,742 resource types in Provider 6.70.0,
cross-checked against its schema, registration code and versioned resource docs.
The table also includes implementation types outside that baseline. Both mode
columns describe input behavior; the baseline notes identify real data sources.
Basic table entries apply to managed resources; verified aliases share only their
documented managed/data capabilities. Omitted data sources retain
reference provenance but have no card or incident path. Service classification alone does
not imply dedicated relationship support. The baseline notes distinguish basic
display from existing rules and identify neutral presentation and unknown-scope fallbacks.

The service mapping/name column records formal service classification and legacy
mapping identifiers, not the displayed badge text or bundled artwork. Resource-specific
display names, dimensions and category colors are documented in [Service labels](icons.md).

Spatial is the initial presentation: verified associations can become edges and
verified routes/members can become child cards. Logical resources remain rows.
The table records defaults; the explicit [Spatial type option](configuration.md#explicit-spatial-types)
can present seven Logical AWS types as independent cards while preserving references.
Unknown roles and unresolved placement are visible fallbacks, not rejected input.
Unlisted types also use these fallbacks, without an icon or dedicated type rule.
AWS `aws_iam_*` and `aws_cloudfront_*` types have global scope even when unlisted;
other unlisted types have unknown regional scope. Non-AWS/non-built-in providers
use Unknown / unresolved spatial / no icon / unknown scope, even for lookalike names.
See [provider identity and inference](models.md).

Regional means eligible with a known static provider region or a verified resource
override. Unsupported overrides, missing/dynamic evidence and historical objects
can leave scope unknown. Account evidence is
independent, including for unknown-region types. See the canonical
[provider configuration/account contract](provider-evidence.md) and
[deployment-scope rules](aws.md#deployment-scopes).

The last column links implementation files containing the exact type literal
(the canonical literal for [verified aliases](aws-inventory.md#verified-resource-aliases));
these are navigation aids to conditional rules, not a promise that a given input
creates an edge. A type can occur as an endpoint, a condition or an exclusion.
The entry file `aws.rs` also defines logical placement and reference labels.
An empty cell means no such exact-literal rule reference was found; generic
Terraform references still apply. Read [AWS proof and managed/data restrictions](aws.md),
[relationship semantics](relationships.md), [route ownership](routes.md) and
[component inference](components.md) for reference/value proofs, deletion/deposed
limits and filtering. Names, literal IDs and proximity alone do not prove relations.

Terraform remote-output resolution lives in the plan layer, also linked below.
Explicit [remote-state mappings](multi-plan.md) can connect complete data-source
output provenance across loaded states; the built-in icon does not establish such
a mapping, and managed resources do not act as remote-state data lookups.
